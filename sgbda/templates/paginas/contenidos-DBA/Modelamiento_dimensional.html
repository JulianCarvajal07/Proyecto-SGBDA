Modelamiento Dimensional

Esta guía explica de forma sencilla y detallada los cuatro pilares del modelamiento dimensional: hechos, dimensiones, granularidad y llaves subrogadas (surrogate keys). Saber identificar correctamente estos cuatro elementos es la base para diseñar cualquier Data Warehouse. A continuación se mostrará el contenido a tener presente:

01

¿Qué es el Modelamiento Dimensional?

Es una forma de organizar la información pensada para que sea fácil y rápida de consultar, en lugar de estar pensada para evitar duplicidad de datos (como sí ocurre en un sistema transaccional normalizado). La idea central es sencilla: separar "lo que se mide" de "por qué ángulos se quiere analizar esa medida".

Una Analogía Sencilla

Piensa en una factura de venta. Lo que se mide es el valor vendido y la cantidad (eso es el hecho). Los ángulos desde donde quieres analizar esa venta son: ¿a qué cliente?, ¿qué producto?, ¿en qué fecha?, ¿en qué tienda? (eso son las dimensiones). El modelamiento dimensional simplemente organiza la base de datos siguiendo esa misma lógica natural con la que un usuario de negocio piensa un reporte.

02

Identificar los Hechos (Fact Table)

Un hecho es un evento medible del negocio: una venta, un despacho, una llamada de un call center, un pago. La tabla de hechos guarda las métricas numéricas de ese evento (cantidades, valores) junto con las llaves que la conectan a cada dimensión relacionada.

¿Cómo identificar un hecho?

Pregúntate: "¿Qué evento del negocio se repite muchas veces y se puede medir con un número?" Si la respuesta es algo como "cada vez que se vende un producto" o "cada vez que se despacha un pedido", ya encontraste un hecho. La regla práctica es: si se puede sumar, contar o promediar, probablemente es un hecho.

Medidas Aditivas

Se pueden sumar sin problema a través de cualquier dimensión (cliente, producto, tiempo). Ejemplo: ValorVenta, CantidadVendida. Son el tipo de medida más común y más simple de trabajar.

Medidas Semi-Aditivas

Se pueden sumar en algunas dimensiones pero no en el tiempo. Ejemplo: SaldoDeInventario. Sumar el saldo de varios días no tiene sentido de negocio (se debe usar el último saldo o un promedio).

Medidas No Aditivas

- No se pueden sumar bajo ninguna dimensión. Ejemplo: un Porcentaje, un Margen % o un Precio Unitario. Estas medidas normalmente se recalculan a partir de otras medidas aditivas (ej: Margen % = Utilidad / Venta), en lugar de sumarlas directamente.

Tabla_de_Hechos.sql 

-- Fact_Ventas: cada fila representa UN evento de venta
CREATE TABLE Fact_Ventas (
    VentaKey     BIGINT PRIMARY KEY,   -- llave subrogada de la tabla de hechos
    ClienteKey   INT REFERENCES Dim_Cliente(ClienteKey),
    ProductoKey  INT REFERENCES Dim_Producto(ProductoKey),
    FechaKey     INT REFERENCES Dim_Fecha(FechaKey),
    TiendaKey    INT REFERENCES Dim_Tienda(TiendaKey),

    -- Medidas (lo que se mide del evento)
    Cantidad     INT,             -- aditiva
    ValorVenta   DECIMAL(18,2)    -- aditiva
);
03

Identificar las Dimensiones (Dimension Table)

Una dimensión responde a las preguntas quién, qué, cuándo, dónde y cómo alrededor de un hecho. Son las tablas que le dan contexto descriptivo a la medida y permiten filtrar, agrupar y desglosar la información en un reporte.

¿Cómo identificar una dimensión?

Pregúntate: "¿Por este campo el usuario de negocio querría filtrar o agrupar el reporte?" Si la respuesta es sí (por ciudad, por categoría de producto, por mes, por vendedor), ese campo pertenece a una dimensión. La regla práctica es: si describe o clasifica algo, es una dimensión; si se mide, es un hecho.

Dimensiones Típicas

Dim_Cliente (nombre, ciudad, segmento), Dim_Producto (nombre, categoría, marca), Dim_Fecha (día, mes, año, trimestre), Dim_Tienda (nombre, ciudad, tipo de tienda).

Dimensión de Fecha (caso especial)

Es la única dimensión que casi siempre se construye manualmente (no viene de un sistema origen), generando una fila por cada día del calendario, con columnas ya calculadas como mes, trimestre, año y nombre del día, para que las consultas de tiempo sean más rápidas y sencillas.

Tablas_de_Dimension.sql 

-- Dim_Cliente: cada fila describe UN cliente
CREATE TABLE Dim_Cliente (
    ClienteKey    INT PRIMARY KEY,     -- llave subrogada
    ClienteID     VARCHAR(20),         -- llave natural (viene del sistema origen)
    NombreCliente VARCHAR(100),
    Ciudad        VARCHAR(50),
    Segmento      VARCHAR(50)
);

-- Dim_Fecha: una fila por cada dia del calendario
CREATE TABLE Dim_Fecha (
    FechaKey  INT PRIMARY KEY,   -- ej: 20250115 (formato AAAAMMDD)
    Fecha     DATE,
    Anio      INT,
    Mes       INT,
    NombreMes VARCHAR(20),
    Trimestre INT,
    DiaSemana VARCHAR(20)
);
04

Granularidad

La granularidad define qué representa exactamente una fila en la tabla de hechos. Es, sin duda, la decisión más importante de todo el modelo dimensional: si se define mal, luego es muy difícil (o imposible) corregirla sin volver a cargar toda la información desde cero.

Preguntas para Definir la Granularidad

- ¿Una fila representa una línea de un pedido, o el pedido completo?

- ¿Se necesita el detalle día a día, o es suficiente un resumen mensual?

- ¿Se necesita saber por vendedor, o solo el total por tienda?

Granularidad Fina (Detallada)

Ejemplo: una fila por cada línea de producto dentro de una factura. Ocupa más espacio y son más filas, pero permite responder cualquier pregunta futura, ya que se puede resumir hacia arriba (por cliente, por mes, por tienda) sin problema.

Granularidad Gruesa (Resumida)

Ejemplo: una fila por total de ventas por tienda y por mes. Ocupa menos espacio y es más rápida de consultar, pero ya no se puede "desagregar": si luego el negocio pide el detalle por producto, no existe forma de recuperarlo desde esa tabla.

Regla de Oro

- Ante la duda, siempre es preferible una granularidad más fina. Es fácil resumir datos detallados hacia un nivel más alto (con un simple `GROUP BY`), pero es imposible partir de un dato ya resumido para recuperar el detalle que nunca se guardó.

Ejemplo_Granularidad.sql 

-- Granularidad FINA: una fila por linea de producto en la factura
-- (permite responder practicamente cualquier pregunta futura)
-- Factura 001 -> Producto A, cant 2
-- Factura 001 -> Producto B, cant 1
-- Factura 002 -> Producto A, cant 5

-- Granularidad GRUESA: una fila por total de la factura
-- (ya no se sabe que productos exactos se vendieron en cada factura)
-- Factura 001 -> Total: 3 unidades
-- Factura 002 -> Total: 5 unidades
05

Llaves Subrogadas (Surrogate Keys)

Una llave subrogada es un identificador generado internamente por el Data Warehouse (normalmente un número autoincremental), que no tiene ningún significado de negocio y que se usa como llave primaria en cada tabla de dimensión, en lugar de usar la llave que trae el sistema origen.

Llave Natural

Es el identificador que ya trae el sistema origen (ej: ClienteID = "CL-4521", una cédula, un código de producto del ERP). Tiene significado de negocio y puede cambiar de formato, ser reutilizado, o incluso repetirse entre distintos sistemas origen.

Llave Subrogada

Es un número propio del DWH (ej: ClienteKey = 1, 2, 3...), sin ningún significado para el negocio, generado únicamente para relacionar las tablas de hechos con las dimensiones dentro del modelo.

¿Por qué se usan en lugar de la llave natural?

- Permiten manejar histórico (SCD Tipo 2): un mismo cliente natural (`ClienteID = "CL-4521"`) puede tener varias filas en el tiempo (una por cada cambio de ciudad), cada una con su propia llave subrogada distinta.

- Independencia del sistema origen: si el código de negocio cambia de formato, o si se integran varias fuentes que usan el mismo código para cosas distintas, la llave subrogada evita conflictos.

- Rendimiento: un número entero es más liviano y más rápido para hacer `JOIN` que una llave de texto larga.

- Manejo de "desconocidos": permite crear un registro especial (ej: ClienteKey = -1, "Cliente Desconocido") para asociar hechos que llegan sin una dimensión válida, sin romper la integridad del modelo.

Llave_Natural_vs_Subrogada.sql 

-- Llave natural (ClienteID) vs Llave subrogada (ClienteKey)
CREATE TABLE Dim_Cliente (
    ClienteKey    INT IDENTITY(1,1) PRIMARY KEY,  -- llave subrogada (autonumerica)
    ClienteID     VARCHAR(20)       NOT NULL,     -- llave natural (viene del origen)
    NombreCliente VARCHAR(100),
    Ciudad        VARCHAR(50),
    FechaInicio   DATE,
    FechaFin      DATE NULL,
    Vigente       BIT
);

-- Ejemplo: el mismo cliente natural con dos versiones historicas (SCD Tipo 2)
-- ClienteKey | ClienteID | Ciudad     | FechaInicio | FechaFin   | Vigente
-- 101        | CL-4521   | Bogota     | 2022-01-01  | 2024-06-30 | 0
-- 205        | CL-4521   | Medellin   | 2024-07-01  | NULL       | 1
06

Ejemplo Integrado: los 4 Conceptos Juntos

A continuación se muestra cómo se aplican los cuatro conceptos en conjunto, tomando como caso de negocio la venta de productos en distintas tiendas.

Definición del Modelo

Granularidad: una fila por cada línea de producto vendido, dentro de cada factura.

Hecho: Fact_Ventas, con las medidas Cantidad y ValorVenta.

Dimensiones: Dim_Cliente, Dim_Producto, Dim_Fecha, Dim_Tienda.

Llaves Subrogadas: ClienteKey, ProductoKey, FechaKey, TiendaKey, generadas todas por el DWH.

Modelo_Completo.sql 

-- DIMENSIONES (contexto descriptivo, llave subrogada como PK)
CREATE TABLE Dim_Cliente (
    ClienteKey INT IDENTITY(1,1) PRIMARY KEY,
    ClienteID  VARCHAR(20),
    Nombre     VARCHAR(100),
    Ciudad     VARCHAR(50)
);

CREATE TABLE Dim_Producto (
    ProductoKey INT IDENTITY(1,1) PRIMARY KEY,
    ProductoID  VARCHAR(20),
    Nombre      VARCHAR(100),
    Categoria   VARCHAR(50)
);

CREATE TABLE Dim_Tienda (
    TiendaKey INT IDENTITY(1,1) PRIMARY KEY,
    TiendaID  VARCHAR(20),
    Nombre    VARCHAR(100),
    Ciudad    VARCHAR(50)
);

CREATE TABLE Dim_Fecha (
    FechaKey INT PRIMARY KEY,
    Fecha    DATE,
    Anio     INT,
    Mes      INT
);

-- HECHO (medidas + llaves subrogadas hacia cada dimension)
-- Granularidad: una fila = una linea de producto dentro de una factura
CREATE TABLE Fact_Ventas (
    VentaKey    BIGINT IDENTITY(1,1) PRIMARY KEY,
    ClienteKey  INT REFERENCES Dim_Cliente(ClienteKey),
    ProductoKey INT REFERENCES Dim_Producto(ProductoKey),
    TiendaKey   INT REFERENCES Dim_Tienda(TiendaKey),
    FechaKey    INT REFERENCES Dim_Fecha(FechaKey),
    NumeroFactura VARCHAR(20),   -- referencia al documento origen
    Cantidad    INT,
    ValorVenta  DECIMAL(18,2)
);
07

Errores Comunes al Modelar

Estos son los errores más frecuentes a la hora de identificar hechos, dimensiones, granularidad y llaves subrogadas, especialmente al iniciar en proyectos de Data Warehouse.

Errores a Evitar

- Mezclar granularidades en una misma tabla de hechos (algunas filas a nivel factura, otras a nivel línea de producto).

- Usar la llave natural como llave primaria de una dimensión, en lugar de crear una llave subrogada propia del DWH.

- Guardar un atributo descriptivo dentro de la tabla de hechos (ej: el nombre del cliente directamente en `Fact_Ventas`), en lugar de dejarlo en su dimensión correspondiente.

- Definir la granularidad demasiado resumida desde el inicio, sin considerar preguntas futuras que el negocio pueda llegar a hacer.

- No contemplar un registro "Desconocido" en las dimensiones, lo que genera errores al llegar hechos sin una relación válida.
