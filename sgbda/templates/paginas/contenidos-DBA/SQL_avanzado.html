SQL Avanzado para Data Warehouse

Esta guía detalla los conocimientos concretos de SQL avanzado que se deben dominar para facilitar el trabajo en un proyecto de Data Warehouse: qué hace cada técnica, cuándo usarla y un ejemplo aplicado. A continuación se mostrará el contenido a tener presente:

01

Funciones de Ventana (Window Functions)

Permiten realizar cálculos sobre un conjunto de filas relacionadas (una "ventana") sin necesidad de agrupar el resultado como lo hace un GROUP BY tradicional, es decir, se puede calcular un agregado y aun así ver el detalle de cada fila. Son la base de la mayoría de reportes analíticos en un DWH: rankings, acumulados, comparativos entre periodos.

¿Cuándo se usan?

- Calcular el top N por categoría (ej: mejor cliente por región).

- Calcular totales acumulados (ventas acumuladas en el año).

- Comparar un valor contra el periodo anterior o siguiente (variación mes a mes).

- Detectar y eliminar duplicados en cargas de staging.

Funciones más usadas

ROW_NUMBER() numera filas de forma única, útil para deduplicar.

RANK() / DENSE_RANK() generan rankings, con o sin saltos al empatar.

SUM()/AVG() OVER() genera acumulados o promedios móviles.

LAG() / LEAD() traen el valor de la fila anterior o siguiente.

Window_Functions.sql 

-- Ranking del cliente con mas ventas dentro de cada region
SELECT ClienteKey, Region, ValorVenta,
       RANK() OVER (PARTITION BY Region ORDER BY ValorVenta DESC) AS Ranking
FROM Fact_Ventas;

-- Total acumulado de ventas ordenado por fecha (running total)
SELECT FechaKey, ValorVenta,
       SUM(ValorVenta) OVER (ORDER BY FechaKey) AS AcumuladoVentas
FROM Fact_Ventas;

-- Comparar la venta del mes actual contra el mes anterior
SELECT FechaKey, ValorVenta,
       LAG(ValorVenta) OVER (ORDER BY FechaKey) AS VentaMesAnterior
FROM Fact_Ventas;
02

CTEs (Common Table Expressions)

Una CTE es una consulta temporal con nombre, definida con WITH, que existe únicamente durante la ejecución de la consulta principal. Ayuda a dividir consultas complejas en pasos legibles, evitando anidar múltiples subconsultas difíciles de leer y mantener.

¿Cuándo se usan?

- Cuando una consulta requiere varios pasos intermedios antes del resultado final.

- Para mejorar la legibilidad de consultas que de otra forma tendrían subconsultas anidadas.

- Las CTE recursivas se usan para recorrer jerarquías, como una estructura organizacional o un árbol de categorías de producto.

Puntos Clave

- Una CTE no se materializa en disco, se resuelve en el momento de ejecutar la consulta.

- Se pueden encadenar varias CTE dentro de un mismo WITH.

- Una CTE recursiva necesita un caso base y un caso recursivo unidos por UNION ALL.

CTE_Simple_y_Recursiva.sql 

-- CTE simple: total de ventas por cliente, filtrado despues
WITH VentasPorCliente AS (
    SELECT ClienteKey, SUM(ValorVenta) AS Total
    FROM Fact_Ventas
    GROUP BY ClienteKey
)
SELECT * FROM VentasPorCliente WHERE Total > 1000000;

-- CTE recursiva: recorrer una jerarquia de categorias de producto
WITH JerarquiaCategoria AS (
    -- Caso base: categorias raiz (sin padre)
    SELECT CategoriaKey, NombreCategoria, CategoriaPadreKey, 0 AS Nivel
    FROM Dim_Categoria
    WHERE CategoriaPadreKey IS NULL

    UNION ALL

    -- Caso recursivo: hijos de la categoria anterior
    SELECT h.CategoriaKey, h.NombreCategoria, h.CategoriaPadreKey, j.Nivel + 1
    FROM Dim_Categoria h
    INNER JOIN JerarquiaCategoria j ON h.CategoriaPadreKey = j.CategoriaKey
)
SELECT * FROM JerarquiaCategoria ORDER BY Nivel;
03

GROUPING SETS, ROLLUP y CUBE

Son extensiones del GROUP BY que permiten obtener varios niveles de agregación en una sola consulta, en lugar de escribir múltiples consultas unidas con UNION. Son muy comunes al construir reportes con subtotales y totales generales, como los que se ven en tablas dinámicas.

¿Cuándo se usan?

- Reportes que necesitan subtotales por región, subtotales por categoría y un total general al mismo tiempo.

- Evitar escribir 3 o 4 consultas distintas unidas con UNION ALL para lograr ese mismo resultado.

Diferencia entre cada una

ROLLUP genera subtotales de forma jerárquica (de derecha a izquierda) y un total general.

CUBE genera todas las combinaciones posibles entre las columnas indicadas.

GROUPING SETS permite definir manualmente cuáles combinaciones específicas se necesitan, sin generar todas.

Rollup_Cube_GroupingSets.sql 

-- ROLLUP: subtotal por region, subtotal por region+categoria y total general
SELECT Region, Categoria, SUM(ValorVenta) AS TotalVentas
FROM Fact_Ventas
GROUP BY ROLLUP(Region, Categoria);

-- CUBE: todas las combinaciones posibles entre region y categoria
SELECT Region, Categoria, SUM(ValorVenta) AS TotalVentas
FROM Fact_Ventas
GROUP BY CUBE(Region, Categoria);

-- GROUPING SETS: solo las combinaciones que se necesitan puntualmente
SELECT Region, Categoria, SUM(ValorVenta) AS TotalVentas
FROM Fact_Ventas
GROUP BY GROUPING SETS ((Region), (Categoria), ());
04

MERGE (Upsert) para Cargas Incrementales

El comando MERGE permite insertar, actualizar o incluso eliminar registros en una sola instrucción, comparando una tabla origen (por ejemplo la zona de staging) contra una tabla destino (una dimensión o hecho del DWH). Es el comando central en cualquier proceso ETL/ELT para cargas incrementales, ya que evita truncar y recargar toda la tabla cada vez.

¿Cuándo se usa?

- Cuando se necesita actualizar registros existentes e insertar los nuevos en un solo paso.

- En cargas incrementales diarias, donde solo llega un subconjunto de datos nuevos o modificados.

- Para mantener sincronizada una tabla de dimensión contra su fuente de origen.

Puntos Clave

- La cláusula ON define la llave de negocio que compara origen y destino.

- WHEN MATCHED actualiza registros que ya existen.

- WHEN NOT MATCHED inserta los registros nuevos que no existían en el destino.

Merge_Upsert.sql 

MERGE INTO Dim_Cliente AS destino
USING Staging_Cliente AS origen
ON destino.ClienteID = origen.ClienteID

WHEN MATCHED THEN
    UPDATE SET destino.Nombre = origen.Nombre,
               destino.Ciudad = origen.Ciudad

WHEN NOT MATCHED THEN
    INSERT (ClienteID, Nombre, Ciudad)
    VALUES (origen.ClienteID, origen.Nombre, origen.Ciudad);
05

PIVOT y UNPIVOT

Permiten transformar filas en columnas (PIVOT) o columnas en filas (UNPIVOT). Son muy usados al construir reportes desde el Data Warehouse, ya que la información suele estar guardada por filas (formato largo), pero el usuario de negocio la necesita ver organizada por columnas (formato ancho), como en una tabla dinámica de Excel.

¿Cuándo se usan?

- PIVOT cuando se necesita mostrar, por ejemplo, una columna por cada mes con el total de ventas de ese mes.

- UNPIVOT cuando la fuente llega en formato ancho (una columna por mes) y se necesita normalizar a formato largo para cargarla correctamente en una tabla de hechos.

Puntos Clave

- El resultado de un PIVOT es más fácil de leer para negocio, pero más difícil de mantener a nivel de código.

- Generalmente se recomienda dejar el PIVOT a la capa de reportes (BI) y mantener el DWH en formato largo.

Pivot_Unpivot.sql 

-- PIVOT: pasar de filas (mes) a columnas (una columna por mes)
SELECT Categoria, [1] AS Enero, [2] AS Febrero, [3] AS Marzo
FROM (
    SELECT Categoria, MES(Fecha) AS Mes, ValorVenta
    FROM Fact_Ventas
) AS Origen
PIVOT (
    SUM(ValorVenta)
    FOR Mes IN ([1],[2],[3])
) AS TablaPivote;

-- UNPIVOT: pasar de columnas (una por mes) a filas
SELECT Categoria, Mes, ValorVenta
FROM Reporte_Ancho
UNPIVOT (
    ValorVenta FOR Mes IN (Enero, Febrero, Marzo)
) AS TablaUnpivot;
06

Manejo de Fechas y Granularidad Temporal

Casi toda tabla de hechos en un Data Warehouse se analiza a través del tiempo (por día, mes, trimestre, año), por lo que dominar el manejo de fechas es indispensable, tanto para construir la Dim_Fecha como para calcular métricas comparativas entre periodos.

Funciones Clave

DATEPART() extrae una parte específica de una fecha (año, mes, día, trimestre).

DATEDIFF() calcula la diferencia entre dos fechas en días, meses o años, útil para calcular antigüedad o tiempos de respuesta.

EOMONTH() obtiene el último día del mes de una fecha dada, muy usado para cierres mensuales.

Truncar a mes/trimestre (ej: DATEFROMPARTS(YEAR(Fecha), MONTH(Fecha), 1)) para agrupar información por periodo sin perder el detalle del día original.

Manejo_Fechas.sql 

-- Extraer año, mes y trimestre de una fecha
SELECT Fecha,
       DATEPART(YEAR, Fecha)    AS Anio,
       DATEPART(MONTH, Fecha)   AS Mes,
       DATEPART(QUARTER, Fecha) AS Trimestre
FROM Dim_Fecha;

-- Ultimo dia del mes (util para reportes de cierre)
SELECT EOMONTH(Fecha) AS UltimoDiaMes
FROM Dim_Fecha;

-- Diferencia en dias entre la fecha de venta y la fecha actual
SELECT DATEDIFF(DAY, Fecha, GETDATE()) AS DiasDesdeVenta
FROM Fact_Ventas;
07

Detección y Eliminación de Duplicados

En la zona de staging es muy común recibir registros duplicados, ya sea porque la fuente los envía repetidos o porque se ejecutó una carga más de una vez. Antes de mover la información hacia el modelo final, se debe garantizar que cada llave de negocio quede una sola vez.

¿Cuándo se usa?

- Justo después de la extracción, dentro de la zona de staging, antes de aplicar el MERGE hacia el modelo final.

- Al depurar cargas históricas donde se sospecha que un mismo archivo se cargó más de una vez.

Eliminar_Duplicados.sql 

-- Se numera cada grupo de duplicados por ClienteID, dejando en 1
-- el registro mas reciente segun FechaCarga
WITH Duplicados AS (
    SELECT *,
           ROW_NUMBER() OVER (
               PARTITION BY ClienteID
               ORDER BY FechaCarga DESC
           ) AS rn
    FROM Staging_Cliente
)
DELETE FROM Duplicados WHERE rn > 1;
08

Índices y Planes de Ejecución

Las tablas de un Data Warehouse suelen manejar grandes volúmenes de información, por lo que un buen manejo de índices y la capacidad de leer un plan de ejecución son claves para que los reportes y las cargas no se vuelvan lentas con el tiempo.

Tipos de Índice

Clustered: define el orden físico de la tabla en disco; solo puede existir uno por tabla.

Non-Clustered: estructura adicional que apunta a las filas, útil para columnas usadas frecuentemente en filtros o `JOIN`.

Columnstore: almacena los datos por columna en lugar de por fila; ideal en tablas de hechos grandes, ya que acelera enormemente las agregaciones (`SUM`, `AVG`, `COUNT`).

Plan de Ejecución

- Muestra cómo el motor de base de datos va a resolver una consulta: qué índices usa, en qué orden hace los `JOIN`, entre otros.

- Un Table Scan o Index Scan sobre una tabla grande suele ser señal de que falta un índice adecuado para esa consulta.

- Revisarlo permite detectar cuellos de botella antes de que un reporte se vuelva lento en producción.

09

Particionamiento de Tablas

Consiste en dividir físicamente una tabla grande en secciones más pequeñas (particiones), generalmente por rango de fechas. Es una práctica habitual en tablas de hechos que acumulan años de historia, ya que mejora tanto el rendimiento de consulta como el de carga.

¿Cuándo se usa?

- En tablas de hechos con millones de registros, particionadas normalmente por año o por mes.

- Permite hacer "switch" o intercambio de partición al cargar históricos completos, cambiando metadatos en lugar de mover fila por fila, lo cual es mucho más rápido.

- Facilita el mantenimiento: se puede reconstruir o archivar una sola partición sin afectar el resto de la tabla.

- El motor puede descartar particiones completas que no aplican a un filtro (partition elimination), acelerando las consultas que ya traen un rango de fechas.

10

Dimensiones de Cambio Lento (SCD)

Las Slowly Changing Dimensions (SCD) son técnicas para manejar los cambios en los atributos de una dimensión a través del tiempo (por ejemplo, cuando un cliente cambia de ciudad). La forma en que se maneje ese cambio depende de si el negocio necesita conservar el histórico o no.

SCD Tipo 1 — Sobrescribir

El nuevo valor reemplaza el anterior, sin dejar rastro del cambio. Se usa cuando el histórico del atributo no es relevante para el negocio (ej: corregir un error de digitación en un nombre).

SCD Tipo 2 — Histórico

Se inserta un nuevo registro con el valor actualizado, conservando el anterior con columnas de control como FechaInicio, FechaFin y Vigente. Se usa cuando el negocio necesita analizar la información tal como era en el momento del hecho (ej: a qué región pertenecía un cliente cuando se realizó la venta).

SCD_Tipo2_con_Merge.sql 

-- Se cierra la version vigente del cliente si algun atributo cambio
UPDATE Dim_Cliente
SET FechaFin = GETDATE(), Vigente = 0
FROM Dim_Cliente destino
INNER JOIN Staging_Cliente origen
    ON destino.ClienteID = origen.ClienteID
WHERE destino.Vigente = 1
  AND (destino.Ciudad <> origen.Ciudad);

-- Se inserta la nueva version vigente con el dato actualizado
INSERT INTO Dim_Cliente (ClienteID, Nombre, Ciudad, FechaInicio, FechaFin, Vigente)
SELECT origen.ClienteID, origen.Nombre, origen.Ciudad, GETDATE(), NULL, 1
FROM Staging_Cliente origen
LEFT JOIN Dim_Cliente destino
    ON origen.ClienteID = destino.ClienteID AND destino.Vigente = 1
WHERE destino.ClienteID IS NULL;
